# Релиз: тег выводится из манифеста плагина

Принято в [#39](https://github.com/Conte777/infra-mcp/issues/39), реализовано в [#41](https://github.com/Conte777/infra-mcp/issues/41).

Плагин не несёт бинаря: запускалка собирает `go install github.com/Conte777/infra-mcp/cmd/infra-mcp-<источник>@v<версия из манифеста>` ([ADR-0002](0002-config-schema-and-degraded-start.md) описывает остальную часть старта). Значит версия в манифесте обязана называть существующий тег, а до этого решения её не держало ничто: бамп манифеста без пуша тега проходил все шесть гейтов CI и ломался только у того, кто поставил плагин, — при первом старте сервера, сообщением `go install`.

## Решения и причины

**Версия — факт уровня репозитория, тег один.** Форму выбрали не мы: `cmd/infra-mcp-postgres` живёт в корневом модуле, поэтому `go install …@v0.1.0` требует тега ровно `v0.1.0` на корне; `postgres/v0.1.0` относился бы к модулю с корнем в `plugins/postgres`, которого нет. Тег один, манифестов будет шесть — значит все шесть несут одинаковую версию, равную тегу.

**Тег выводится из манифеста, а не набирается вторым разом.** Ставит его workflow: триггер `workflow_run` по успешному завершению `ci` на `main`, чекаут по `head_sha`, `contents: write`. Релиз становится одним действием — смержить PR с бампом, — и забывать больше нечего.

**Логика идемпотентная, а не событийная.** Прочитать версию, `git rev-parse` по тегу: есть — выйти, нет — создать и запушить. «В пуше изменился `plugin.json`» не подходит: у `workflow_run` нет фильтра по путям, а ре-ран обязан быть безопасен. Отсюда же полная история при чекауте — существующие теги и есть то, что делает повторный прогон пустым.

**Триггер — `workflow_run`, а не `push: branches: [main]`.** Пуш стартовал бы параллельно матрице `check` и мог поставить тег на красный `main`; `workflow_run` по построению видит уже зелёный прогон и берёт ровно тот коммит, который тестировался (`head_sha`), а не то, куда `main` уехал за это время.

**Согласие манифестов держит Go-тест** в идиоме `schema:check`: едет в `task test`, отдельного гейта в матрице CI не заводит. Сегодня плагин один и цена нулевая; при шести расхождение — неработающая запускалка у пяти из них. `task version:set -- X.Y.Z` переписывает манифесты разом; это удобство, а не гарантия.

**`buildinfo.version` выброшен.** Хук под `-ldflags` не заполнял никто: ни `Taskfile.yml`, ни CI не передают флагов, а единственная живая причина его заполнять — чтобы `task build` из клона знал свою версию — упирается в то, что взять её можно только из манифеста, и тогда бинарь из грязного дерева объявил бы себя `v0.1.0`, `IsRelease()` поверил бы и построил ссылку на схему конфига по тегу, где Go-тип конфига уже другой. `(devel)` честен именно тем, что молчит. Хук вернётся одной строкой вместе с тем, что его наполнит.

**Провал сборки в запускалке оборачивается своей строкой.** Сырой `unknown revision v0.1.0` в Claude Code выглядит как «сервер не стартовал», и догадаться о несостоявшемся релизе по нему нельзя; исходный вывод `go` остаётся выше, своя строка добавляется под ним.

## Отвергнутые варианты

- **Гейт в CI на пуш тега** («тег `vX` обязан совпасть с манифестом того же коммита») — первое, что приходит в голову, и оно срабатывает после публикации. Тег необратим: `proxy.golang.org` кеширует ревизию при первом запросе, переставленный или удалённый тег остаётся в кеше навсегда, и починка ошибочного релиза возможна только следующей версией вперёд. Красный чек рядом с необратимым тегом ничего не спасает.
- **Релизный чек-лист без автоматики** — вся постановка вопроса началась с забытого второго шага.
- **Проверка тега до сборки в запускалке** (`git ls-remote`, запрос к proxy) — тот же диагноз ценой сетевого вызова на каждом холодном старте.
- **GitHub Release вместе с тегом** — тег это всё, что нужно `go install`; релиз с артефактами появится вместе с goreleaser, который в эталон не входит.

## Следствия

- **Тег, созданный через `GITHUB_TOKEN`, не запускает другие workflow** — GitHub так гасит петли событий. Сегодня на пуш тега не висит ничего, но это мина под будущий goreleaser: его workflow с `on: push: tags` не сработает, понадобится PAT или `workflow_dispatch`.
- **Первый настоящий релиз — первый прогон машинки.** Тегов в репозитории не было вообще, а манифест уже говорил `0.1.0`: плагин в `main` был неработоспособен для любого, кто его поставит. `v0.1.0` ставится закрытием [#11](https://github.com/Conte777/infra-mcp/issues/11).
- **Запускалка покрыта Go-тестом**, а не только `sh -n`: тест гоняет сам скрипт со стабом `go` через существующий шов `${INFRA_MCP_GO:-go}` и временным `XDG_CACHE_HOME`.

## Состояние в коде

Релизный workflow — `.github/workflows/release.yml`: один шаг, читает версию `jq` по всем `plugins/*/.claude-plugin/plugin.json` и требует, чтобы после `sort -u` осталась одна строка (тикет называл конкретный манифест postgres; глоб не привязывает workflow к имени плагина и заодно перепроверяет согласие).

Гейты манифеста — `plugins/manifest_test.go`: `TestManifestVersionsAgree` и `TestManifestVersionIsATagWithoutThePrefix` (префикс `v` принадлежит тегу, а не манифесту). Запускалка — `plugins/launcher_test.go`: извлечение версии `sed`'ом, вытеснение прошлых версий из кеша, обёртка провала сборки, манифест без версии. Оба файла — единственное содержимое пакета `plugins`, кода в нём нет.

Версия бинаря — `internal/buildinfo`: `Version()` спрашивает `debug.ReadBuildInfo()`, `IsRelease()` отсеивает псевдоверсии и `+dirty`; таблица случаев проверяет неэкспортируемую `isRelease`, потому что подменить версию снаружи больше нечем.

Запускалка — `plugins/postgres/bin/infra-mcp-postgres`: вытеснение кеша сделано циклом по `"$cache"/*`, а не `find -mindepth/-maxdepth`, — не ради переносимости (BSD и GNU его знают), а потому что строка, сносящая каталоги, должна читаться без сноски.
