# Стенды и кластеры: три уровня конфига, адрес вызова и граница ядра

Принято при построении карты [#47](https://github.com/Conte777/infra-mcp/issues/47), реализовано в [#48](https://github.com/Conte777/infra-mcp/issues/48), [#49](https://github.com/Conte777/infra-mcp/issues/49) и [#50](https://github.com/Conte777/infra-mcp/issues/50).

Один процесс сервера обслуживает все стенды и все кластеры пользователя. Конфиг источника — один файл `~/.config/infra-mcp/<источник>.json` в три уровня: глобальный, стенд, кластер; нижний переопределяет верхний. Инструмент адресуется тремя обязательными аргументами — стенд, кластер и сегмент источника (у postgres это база). Стенды и кластеры принадлежат **ядру**: остальные пять источников получают их клонированием, ничего не реализуя.

До этого решения второй стенд стоил второго процесса: [ADR-0002](./0002-config-schema-and-degraded-start.md) знал «файл на профиль», профиль задавался флагом `--profile`, и prod от dev отделяла физическая изоляция — разные процессы с разными конфигами. Это не масштабируется на шесть источников: пользователь с тремя стендами ставил бы восемнадцать серверов руками, и Claude Code запускал бы восемнадцать процессов.

## Решения и причины

**Форма файла — три уровня, карта имён на каждом.**

```json
{
  "connection": { "user": "app", "password": "${PGPASSWORD}" },
  "environments": {
    "dev": {
      "connection": { "host": "dev.example.com" },
      "clusters": { "main": { "databases": { "default": "app_db" } } }
    },
    "prod": {
      "readOnly": true,
      "clusters": {
        "main": {
          "connection": { "host": "prod.example.com" },
          "databases": { "default": "app_db", "exclude": ["*_tmp"] }
        }
      }
    }
  }
}
```

Карта имён, а не массив объектов с полем `name`: уникальность имени обеспечивает сам JSON, а не проверка в `Validate`, и имя не пишется дважды. Ключи кластера пишутся **прямо в объект уровня**, рядом с `environments`/`clusters`, а не в отдельную группу `defaults`: тогда «что унаследуется» — это в точности «что можно написать в кластере», и второго набора имён не заводится.

**Наследование делает ядро слиянием сырого JSON**, до декодирования в тип источника (`mcpsrv.inherit`). Объекты сливаются по ключам; всё остальное — скаляр, список — заменяется целиком, поэтому список никогда не наследуется наполовину. Ядру при этом не нужно знать ни одного имени поля источника: своих ключей у него на уровне два, `environments` и `clusters`, остальное — непрозрачный объект, который оно переносит между уровнями не читая.

Альтернатива — сливать уже разобранные Go-структуры — требует превратить каждое поле каждого из шести источников в указатель: иначе `"sslmode": ""` не отличить от «ключ не задан», и пустая строка снизу затирала бы значение сверху. Плюс функция слияния на каждый тип, в которую забыть новое поле можно молча. Сырой JSON не различает «пусто» и «не задано» по построению — ключа в объекте просто нет.

**Граница ядра и источника проведена по адресу.** Ядро владеет `environments`/`clusters`, именами, `readOnly`, наследованием и **первыми двумя сегментами** адреса. Источник объявляет **тип конфига кластера** — первый параметр `Common[Cluster, ReadTools]`, — и владеет **третьим** сегментом адреса: у postgres это база, у k8s будет неймспейс или контекст. Тот же тип источник встраивает в свой конфиг рядом с `Common` — так глобальный уровень *есть* объект кластера, чем форма файла выше и держится в Go.

Обобщается это сразу, без второго пользователя, — в отличие от кеша пулов, который [ADR-0003](./0003-core-owns-the-process.md) сознательно оставил в источнике до второго примера. Разница в том, что обобщается: там — **механизм** (стоимость соединения и смысл `idleTimeout` у clickhouse и k8s неизвестны), здесь — **форма конфига**, одинаковая у всех шести по построению. «Список именованных экземпляров, сгруппированных по стендам, с наследованием сверху вниз» не зависит от того, что за экземпляр; ровно ради такого разделения ADR-0003 и оставляет источнику только его домен.

**Адрес — три обязательных аргумента, ни одного с дефолтом.** `mcpsrv.Address` (`environment`, `cluster`) встраивается в аргументы инструмента, констрейнт `Addressed` с неэкспортированным методом не даёт зарегистрировать инструмент без него, источник дописывает третий. Печать — `dev/main/orders`, тем же `Address.String()` в отказах, логах и инвентаре.

Одна строка `<стенд>_<кластер>_<база>` отвергнута: `_` законно живёт в именах баз (`order_service`), и разбор держался бы на запрете `_` в именах стендов — правиле, которое пользователь узнаёт из ошибки. Подстановка единственного стенда, когда он в конфиге один, отвергнута отдельно: она заводит класс ошибок «конфиг дополнили вторым кластером, и вчерашние вызовы стали отказывать», а на проде «я не указал стенд» не должно значить «попал куда-то».

**`readOnly` — отказ по адресу, а не урезанный набор инструментов.** Ключ стоит на стенде или на кластере, наследуется общим механизмом, дефолт `false`. Write-инструмент по такому адресу отвечает `KindDenied`; сам инструмент не скрывается — он один на все адреса, а набор инструментов не может зависеть от конфига, иначе allow-строка permissions, глобящая `pg_read_*`, начинает зависеть от того, загрузился ли конфиг ([ADR-0001](./0001-postgres-tool-set-and-boundaries.md)).

Это замена физической изоляции прода, исчезающей вместе с отдельным процессом. Дефолт `true` отвергнут: он делает пустой конфиг молча непишущим, и первым действием человека станет копипаст `"readOnly": false` во все кластеры не глядя — ключ, который все выключают не читая, не защищает ничего.

**Видимость баз — `include` и `exclude`, оба глобами.** Непустой `include` — белый список, пустой — весь кластер; `exclude` вычитается после. Прежний булев `showAll` удалён: «показывать всё» выражается пустым `include` и не требует своего ключа, а «показывать три из тридцати» он не выражал вовсе.

**`databases.default` — точка входа для каталожных запросов**, с дефолтом `postgres`, и никакой привилегии у него нет. Точка входа нужна, потому что `pg_database` не прочитать, не подключившись к какой-нибудь базе, а `initdb` создаёт `postgres` на любом кластере. Достижимость её решают `include`/`exclude` наравне со всеми: иначе `include: ["orders"]` — то есть «мне нужна ровно одна база» — молча давал бы две. Поэтому же снята прежняя проверка «`exclude`, накрывающий `default`, — ошибка конфига»: раз точка входа ничем не привилегирована, накрыть её `exclude`'ом — законный способ сказать «подключайся сюда, но не работай здесь».

**Наследуется всё, что внутри кластера** — включая `pool.maxDatabases` и `databases`, у которых по ходу были свои претензии на исключение. Правило одно, исключений нет: у источника должна остаться **ровно одна** форма конфига кластера, иначе ядру приходится принимать два типа уровня вместо одного, а группа вроде `pool` живёт на двух уровнях с разными ключами. У `databases` цена исключения другая и выше: «какие базы видны — свойство кластера» звучит убедительно, но вынуть его из наследования можно только тегом вроде `mcpsrv:"noinherit"` — то есть завести **в ядре** второе правило поверх «нижнее побеждает», ради одного ключа одного источника. Довод «список унаследуется наполовину» при этом не возникает: списки при слиянии заменяются целиком.

`output` и `tools` при этом остаются глобальными — это свойства сервера и модели, а не кластера, и в тип кластера они не входят.

**Инвентарь стендов и кластеров печатается в `instructions`.** С тремя обязательными аргументами и без дефолтов модель, не зная имён, не может вызвать даже `list_databases`, а `instructions` отдаются при `initialize` — раньше любого вызова. Список печатает **ядро**, приклеивая его к константному тексту источника: имена и `readOnly` принадлежат ему, и передача конфига в `Source.Instructions()` заставила бы шесть источников печатать один и тот же список шесть раз.

[ADR-0001](./0001-postgres-tool-set-and-boundaries.md) запрещает повторять в описаниях **список баз**, и различие здесь существенное: список баз живой, длинный и требует подключения, которого при `initialize` ещё нет; список стендов и кластеров статичен, лежит в файле и читается без единого соединения. Потолка на его длину нет — урезанный список не полный и всё равно длинный, а модель не узнает, что чего-то не видит.

**Один файл на источник, профиль исчезает как понятие.** Единственной работой профиля было дать второй набор настроек ценой второго процесса, и эта карта её отбирает. `--profile` удалён, XDG-путь стал `infra-mcp/<источник>.json`, порядок поиска сократился до `--config` → `INFRA_MCP_<ИСТОЧНИК>_CONFIG` → XDG.

**Ломаем без совместимости.** Пользователей нет, версия — 0.2.0. Конфиг 0.1 — это ровно этот файл с ключами источника, оставшимися на верхнем уровне, поэтому он узнаётся отсутствием `environments` **до** валидации схемой: иначе он получил бы ворох жалоб на неизвестные ключи и ни слова о том, что их заменило. Проверка сознательно не смотрит на `connection` — ядро не знает имён полей источника, — и текст не утверждает, что файл именно 0.1, а называет, куда переезжают настройки подключения.

## Отвергнутые варианты

- **Три записи в `.mcp.json` плагина** (`postgres-dev`/`postgres-stage`/`postgres-prod`). Установка осталась бы одной командой, и ломать конфиг не пришлось бы вовсе. Но имена стендов у каждого пользователя свои — в манифест плагина их не зашить, — процессов стало бы три на источник, а allow-строка permissions умножилась бы на три: имя сервера входит в `mcp__plugin_…__pg_read_*`.
- **Слияние разобранных Go-структур** — цена в указателе на каждое поле каждого из шести источников, разобрана выше.
- **`showAll`** — булев ключ, не выражающий «три из тридцати».
- **Дефолт `readOnly: true`** — ключ, который выключают не читая.
- **`pool.maxDatabases` потолком процесса.** В ходе грилинга он был им сделан и затем пересмотрен: потолок процесса — это второй уровень для группы `pool`, то есть вторая форма конфига у источника. Цена пересмотра — потолок перестаёт быть потолком процесса: десять кластеров по четыре дают до сорока пулов в пределе. Практически сессия трогает один-два кластера, а пул создаётся только при обращении.
- **Совместимость со старой формой** — ветка в загрузчике и вторая форма в схеме навсегда, при нулевом числе пользователей.

## Следствия

- **Глобальный уровень принимает `readOnly`** — прямое следствие того, что глобальный уровень *есть* объект кластера. Наследуется вниз и работает; запрещать пришлось бы отдельной проверкой ради запрета.
- **Обязательных ключей в схеме больше нет.** Значение может прийти с любого из трёх уровней, поэтому схема не требует `connection.host`/`user`/`password` нигде, а присутствие проверяет `Config.Validate` на собранном конфиге кластера — там, где ключ наконец отсутствует. Обязателен в схеме только `environments`.
- **Проверка секретов идёт по уровням**, а не по документу целиком: глобальный, уровень стенда и собранный конфиг кластера. Литерал, написанный на стенде и перекрытый каждым кластером под ним, иначе не попал бы ни в одну проверку.
- **Генератор схемы не умеет уровень стенда.** Go не умеет встраивать параметр типа, поэтому `Environment[Cluster]` объявляет только карту кластеров, и ключи кластера на уровне стенда генератору взять неоткуда. Ядро копирует их из схемы кластера, которую генератор построил сам (`spliceEnvironmentLevel`), — форма конфига не менялась, менялся способ её описать, и ядро по-прежнему не называет ни одного поля источника. Коллизия имени кластерного ключа с ключом ядра — ошибка сборки схемы, а не молчаливая перезапись.
- **Ключ кеша пулов — тройка** стенд/кластер/база: иначе два кластера с базой `orders` делили бы один пул. Вытеснение по `maxDatabases` идёт внутри кластера, `eagerInit` греет точку входа каждого кластера отдельной горутиной — недоступный prod не должен задерживать dev.
- **Дефолт видимости перевернулся с «закрыто» на «открыто»**: `showAll` по умолчанию был `false`, и кластер без ключей доставал одну базу; пустой `include` — это весь кластер. Конфиг, полагавшийся на старый дефолт, после обновления молча расширяется, а не падает. Строка в [CHANGELOG](../../CHANGELOG.md) под 0.2.0 ([#53](https://github.com/Conte777/infra-mcp/issues/53)).
- **`mcpsrv.Env` переименован в `Process`** — слово «environment» занято стендом, и тип, отвечающий про процесс, не может носить его.
- **Отказ по неизвестному адресу адресов не перечисляет.** Полный список лежит в `instructions` той же сессии, и отказ, повторяющий его, платит контекстом за уже полученное; подсказка отправляет туда.
- **`pg_read_status` печатает таблицу «стенд / кластер / readOnly»** — без хоста и без состояния пула. Хост лёг бы в контекст сессии, которая может ни разу не пойти в этот кластер, а путь конфига в той же выдаче ведёт человека к файлу; состояние пула при ленивой инициализации говорит «сегодня туда не ходили», а не «кластер отвечает».

## Состояние в коде

`internal/mcpsrv/cluster.go` (`Address`, `Addressed`, `ClusterCommon`, `Environment`, `Inventory`, `inherit`), `internal/mcpsrv/config.go` (`Common`, `Load` по уровням, `Location` без профиля), `internal/mcpsrv/schema.go` (`spliceEnvironmentLevel`), `internal/mcpsrv/registry.go` (`call` — резолв адреса и отказ по `readOnly`), `internal/mcpsrv/instructions.go` (инвентарь), `internal/mcpsrv/status.go` (`Process`, таблица кластеров); `internal/source/postgres/config.go` (тип `Cluster`, `Databases`, `Validate`), `internal/source/postgres/lease.go` (`Args`, `ConnectionArgs`, `resolveDatabase`), `internal/source/postgres/pool.go` (ключ кеша тройкой), `internal/source/postgres/source.go` (`warm` по кластерам, текст `instructions`), `schema/postgres.schema.json`. Адресация и отказ по `readOnly` проверяются через настоящий MCP-транспорт в `internal/source/postgres/address_integration_test.go`.

Что эта форма конфига значит для остальных пяти источников, здесь не решено: совпадёт ли «кластер» с тем, что у k8s является контекстом, а у grafana — инстансом, и что встанет третьим сегментом адреса, покажет второй источник — он же и проверит границу.
